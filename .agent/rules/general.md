# General Implementation Rules

## Code Style & Standards

### Language-Specific Guidelines

**Python**
- Follow PEP 8 style guide
- Use type hints for function signatures
- Maximum line length: 100 characters
- Use descriptive variable names (no single letters except in comprehensions/loops)
- Docstrings for all public functions (Google style)

**Example:**
```python
def fetch_active_goals(period_type: str, period: str) -> list[dict]:
    """
    Fetch active goals for a specific period from Notion.
    
    Args:
        period_type: Type of period (Yıllık, Çeyreklik, Aylık, Haftalık)
        period: Period identifier (e.g., "2026", "2026-Q1", "2026-01")
        
    Returns:
        List of goal dictionaries with properties and relations
    """
    pass
```

### Naming Conventions

**Files & Directories**
- Python files: `snake_case.py`
- Scripts: `snake_case.py` in `/scripts`
- Modules: `snake_case/` directories

**Code Elements**
- Functions: `snake_case()`
- Classes: `PascalCase`
- Constants: `UPPER_SNAKE_CASE`
- Private methods: `_leading_underscore()`

**Notion Property Names (Turkish)**
- Use Turkish names exactly as specified in schema
- Examples: `Ad`, `Sütun`, `Durum`, `Tarih`
- Keep consistent with implementation plan

## Architecture Patterns

### Separation of Concerns

```
orchestration/
├── notion_client.py      # Direct Notion API wrapper
├── context_builder.py    # Context aggregation logic
├── context_generator.py  # File generation orchestration
└── main.py              # CLI entry points
```

**Rules:**
- `notion_client.py`: Only Notion API calls, no business logic
- `context_builder.py`: Data transformation, no I/O
- `context_generator.py`: Orchestrates client + builder
- `main.py`: CLI parsing, user interaction

### Error Handling

**Always handle API errors gracefully:**
```python
try:
    response = client.databases.query(database_id=db_id)
except APIResponseError as e:
    print(f"Error fetching data: {e}")
    sys.exit(1)
```

**Provide helpful error messages:**
- Include context about what failed
- Suggest next steps
- Log errors for debugging

## Configuration Management

### Environment Variables

**Required Variables** (in `.env`):
- `NOTION_TOKEN`: Integration token
- `NOTION_PAGE_ID`: Parent page ID
- Database IDs (generated by setup script)

**Loading Pattern:**
```python
from dotenv import load_dotenv
import os

load_dotenv()

NOTION_TOKEN = os.getenv("NOTION_TOKEN")
if not NOTION_TOKEN:
    raise ValueError("NOTION_TOKEN not found in environment")
```

## Data Handling

### Notion API Responses

**Always validate response structure:**
```python
def safe_get_property(page, prop_name, prop_type):
    """Safely extract property from Notion page object."""
    try:
        prop = page["properties"][prop_name]
        if prop["type"] != prop_type:
            return None
        # Type-specific extraction logic
    except (KeyError, TypeError):
        return None
```

## CLI Design Principles

### Command Structure

```bash
personalaxis <command> [options]
```

**Commands:**
- `daily-context`: Generate daily context
- `save-journal`: Save journal entry
- `weekly-review`: Generate review context
- `save-review <type>`: Save review session
- `sync`: Sync from Notion
- `habits`: Show today's habits

### User Feedback

**Progress Indicators:**
```python
print("Fetching pillars from Notion...")
print("✓ Retrieved 5 active pillars")
print("Generating context file...")
print("✓ Context saved to output/context.md")
```

**Clear Success/Failure:**
- Use checkmarks (✓) for success
- Use crosses (✗) for failures
- Provide actionable next steps

## Testing Guidelines

### Unit Tests
- Test each function in isolation
- Mock Notion API calls
- Focus on data transformations

### Integration Tests
- Test full workflows (context generation → file creation)
- Use test Notion workspace
- Verify output format

### Manual Testing Checklist
- [ ] Can fetch all database types
- [ ] Context files are properly formatted
- [ ] Relations between databases work
- [ ] Error messages are helpful

## Security & Privacy

**Never commit:**
- `.env` files with real tokens
- Notion database IDs
- Personal journal data
- API keys

**Git Ignore:**
```gitignore
.env
output/
*.pyc
__pycache__/
.DS_Store
```

## Documentation Standards

### Code Comments

**When to comment:**
- Complex algorithms or logic
- Non-obvious decisions
- Workarounds for API limitations
- Business logic tied to Notion schema

**When NOT to comment:**
- Obvious code
- Redundant explanations
- Instead, use better variable names

### README Files

Each module should have:
- Purpose
- Key functions
- Usage examples
- Dependencies

## Language Consistency

**Turkish (Notion-facing):**
- Database names and properties
- Context file content
- User-facing output
- Journal entries

**English (Code-facing):**
- Function and variable names
- Code comments
- Documentation
- Error messages in logs
- AI system prompts

**Rationale:**
- Turkish improves user experience with Notion
- English maintains code readability and international standards
- Clear separation prevents confusion

## Deployment & Execution

- Use virtual environment (venv)
- Install from requirements.txt
- Run from project root

## Version Control

**Commit Messages:**
- Use imperative mood: "Add feature" not "Added feature"
- Be specific: "Implement daily context generation" not "Update code"
- Reference issues/tasks when applicable

**Branch Strategy:**
- `main`: Stable, working code
- Feature branches: `feature/context-builder`
- Use Pull Requests for review (if team grows)

## Future-Proofing

**Design for Extension:**
- Keep Notion schema flexible
- Make database IDs configurable
- Support multiple users (future)
- Allow custom prompt templates

**Deprecation Strategy:**
- Mark deprecated functions with `@deprecated` decorator
- Provide migration guides
- Maintain backwards compatibility for 1 version
